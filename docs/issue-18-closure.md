# Issue #18 关闭总结

## 实践结果

经过完整的集成测试，外部 Godot 场景的引入受到架构限制：

### ✅ 成功案例：Truck Town
- **项目**：godot-demo-projects/3d/truck_town (静态 GLTF 模型)
- **状态**：完全可用
- **性能**：8-10 fps (1920×1080)
- **集成方式**：Nix flake input + 环境变量

### ❌ 失败案例：Realistic Environments
- **项目**：Godot-RealisticEnvironments (海洋、天空插件系统)
- **问题**：渲染结果为空白背景，海洋和天空系统未显示
- **原因**：依赖运行时 GDScript 执行（`_process()`, `_physics_process()`）

## 根本原因

当前系统采用"静态快照"架构：

```
Python (控制场景逻辑) → 静态快照 → Godot (纯渲染器)
```

**设计目标**：
- 保证实验的确定性和可重现性
- Python 完全控制时间推进和真值生成
- Godot 不执行场景脚本，仅渲染静态内容

**适用场景**：
- ✅ 静态几何模型（GLTF、网格）
- ✅ 着色器效果（可通过 uniform 参数控制）
- ✅ Python 可计算的程序化内容

**不适用场景**：
- ❌ 需要 GDScript 插件的系统（海洋、粒子、天气）
- ❌ 依赖场景树更新逻辑的动态效果
- ❌ 需要物理引擎的交互场景

## 已完成的工作

尽管 Realistic Environments 不可用，但集成工作仍有价值：

1. **Nix 外部项目集成流程** (`flake.nix` + 环境变量)
2. **Godot 导入超时优化** (120s → 600s，解决大型项目导入问题)
3. **完整的集成文档** (`docs/nix-external-projects.md`)
4. **架构限制分析** (为未来决策提供依据)

**分支**：`codex/realistic-environments` (已推送，代码保留供参考)

## 决定

**暂不引入外部复杂场景工程。**

**理由**：
1. 大部分优质场景都依赖运行时脚本（海洋、天气、粒子）
2. 修改架构支持脚本执行会牺牲确定性
3. 自研场景更符合科研工具的需求

## 替代方案

**方向 1：提取开源资源** (短期，高性价比)
- 从优秀项目中提取 shader、纹理、模型
- 集成到我们可控的静态场景系统
- 保持确定性和可重现性

**方向 2：增强自研场景** (中期，见 Issue #XX)
- 改进 Hannover 地景的视觉质量
- 解决 Manhattan 高楼建模问题
- 添加天气效果（shader 实现）

**方向 3：混合架构** (长期，如果确实需要)
- 允许白名单脚本在 Python 控制下运行
- 明确标注使用了脚本的场景
- 权衡确定性与功能复杂度
