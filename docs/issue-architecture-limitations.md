# Issue: 静态快照架构限制与未来扩展方向

## 背景

当前系统采用"静态快照"架构：Python 控制场景逻辑和实验时钟，每帧生成静态快照发送给 Godot，Godot 仅作为渲染器不执行场景脚本。

这个设计确保了：
- ✅ 实验的确定性和可重现性（固定随机种子）
- ✅ Python 拥有完整的真值控制
- ✅ 场景状态可独立验证（不依赖 Godot 内部状态）

## 架构说明

```
┌─────────────────────────────────────┐
│ Python (chongming)                   │
│  - ScenarioSpec → LogicalSceneSnapshot (每帧)
│  - 实验时钟 (CaptureTime)           │
│  - 几何计算、投影、遮挡判断          │
│  - 真值生成                          │
└──────────────┬──────────────────────┘
               │ JSON over TCP
               ↓
┌─────────────────────────────────────┐
│ Godot (worker.gd)                    │
│  - 接收快照 → 更新场景树             │
│  - 纯渲染：Camera.render() → RGB8   │
│  - UPDATE_DISABLED (不自动循环)     │
│  - 不执行 _process() / _physics_process()
└─────────────────────────────────────┘
```

## 当前能力范围

### ✅ 支持的内容

1. **静态几何**
   - 球体、盒子、三角网格
   - GLTF/GLB 模型
   - 高度网格地形
   - OSM 建筑挤出

2. **着色器效果**
   - 大气散射（天空颜色）
   - 程序化云层（噪声纹理）
   - 植被风摆（顶点着色器）
   - 指数雾（距离雾）
   - 所有通过 uniform 参数控制的效果

3. **程序化内容（Python 计算）**
   - 植被放置
   - 地形细节
   - 动态光照方向（太阳位置）

### ❌ 不支持的内容

1. **需要 GDScript 的插件系统**
   - 海洋系统（FFT 波浪、浮力计算）
   - 粒子系统（雨、雪、烟雾）
   - 复杂天气系统（体积云、闪电）
   - 音频系统

2. **依赖场景树逻辑**
   - AnimationPlayer 驱动的动画
   - 物理引擎交互（碰撞、反弹）
   - AI 行为树
   - 游戏逻辑脚本

3. **需要墙钟时间**
   - 基于 `OS.get_ticks_msec()` 的动画
   - 实时网络交互
   - 异步资源加载

## 预期影响场景

根据当前计划，以下功能**最有可能**受限制影响：

### 1. 高级天气效果（中概率）

**需求**：真实的雨、雪、雾粒子系统

**限制**：Godot 的 GPUParticles3D 需要 `_process()` 更新发射器

**解决方案**：
- **方案 A（推荐）**：使用 shader 实现（雨滴屏幕效果、雾的体积散射）
- **方案 B**：Python 计算粒子位置，发送为静态几何
- **方案 C**：标注为"视觉近似"，不提供逐粒子真值

**优先级**：中（用户指南已说明不支持高级传感器效应和气象雾）

---

### 2. 真实海洋/水面（低概率）

**需求**：FFT 波浪、船只浮力、水花

**限制**：海洋插件依赖 GDScript 计算波浪高度

**解决方案**：
- **方案 A**：使用简化的 shader 水面（法线贴图 + 反射）
- **方案 B**：Python 实现 FFT 海洋算法（工作量大）
- **方案 C**：不支持，场景避免水面交互

**优先级**：低（目标是空中飞行物，不与水面交互）

---

### 3. 复杂植被动画（低概率）

**需求**：树木摇摆、草丛互动、程序化生长

**限制**：复杂骨骼动画需要 AnimationPlayer

**解决方案**：
- **当前实现**：顶点着色器风摆（已支持）
- **增强**：多层级风摆（主干 + 树枝 + 叶片）
- **不支持**：基于物理的碰撞（鸟撞树枝）

**优先级**：低（当前卡片植被足够）

---

### 4. 引入复杂外部场景（已验证，高概率）

**需求**：使用开源高质量场景（如 Realistic Environments）

**限制**：大部分优质场景依赖运行时脚本

**解决方案**：
- **方案 A（当前方向）**：提取资源（shader、模型、纹理），不用脚本
- **方案 B**：只使用静态场景（如 Truck Town）
- **方案 C**：实现混合架构（见下文）

**优先级**：已评估，暂不修复

---

## 未来扩展方向

如果上述限制成为实际瓶颈，有以下扩展路径：

### 扩展 1：增强 Python 侧计算能力（推荐）

**原则**：保持静态快照架构，用 Python/NumPy 实现复杂算法

**示例**：FFT 海洋
```python
class FFTOceanGenerator:
    def __init__(self, seed: int):
        self.rng = np.random.default_rng(seed)
    
    def generate_mesh(self, time: float) -> TriangleMeshGeometry:
        # 确定性的 FFT 计算
        heights = self._fft_ocean(time)
        return self._build_mesh(heights)
```

**优势**：
- ✅ 保持确定性
- ✅ 可在 GPU 外验证
- ✅ 完全控制

**劣势**：
- ⏱️ 开发工作量
- ⚠️ 性能可能不如 GPU（但离线录制可接受）

---

### 扩展 2：混合架构（谨慎使用）

**原则**：允许白名单脚本在 Python 控制下运行

**实现要点**：
```python
# Python 端
renderer.enable_script("res://addons/ocean/ocean.gd")
renderer.update(snapshot, delta_time=0.033)  # 明确传递时间增量
```

```gdscript
# Godot 端
func update_scene(snapshot, delta_time):
    # 1. 应用静态快照（目标、相机）
    apply_snapshot(snapshot)
    
    # 2. 用 Python 的 delta，不是墙钟
    for script in _whitelisted_scripts:
        script._process(delta_time)
```

**要求**：
- 脚本使用固定随机种子
- 禁用墙钟访问
- 明确标注使用脚本的场景
- 验证多次运行的一致性

**优势**：
- ✅ 可使用复杂插件

**劣势**：
- ⚠️ 确定性依赖脚本实现（不可控）
- ⚠️ 需要逐个验证插件
- ⚠️ 调试困难
- ⚠️ 增加系统复杂度

**触发条件**：
- 需要的效果**无法用 shader 实现**
- Python 复现算法**成本过高**
- 确定性可以**部分妥协**（如"视觉近似，不影响真值"）

---

## 当前决定

**保持静态快照架构，不做修改。**

**理由**：
1. 当前和可预见的需求都能满足
2. 确定性是科研工具的核心价值
3. 着色器足够强大（程序化几何、视觉效果）
4. 如果真遇到瓶颈，有增量扩展路径
5. 不应为"可能用到"而重构核心架构

**重新评估时机**：
- 用户明确要求某个当前不支持的效果
- 该效果对实验结果有实质影响（不是纯视觉）
- 用 shader 或 Python 实现成本确实过高
